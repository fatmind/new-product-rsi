# 本体：世界对象 + 关系

> 用在四个地方 —— 函数说明书的输入输出字段、造数据的对象清单、落盘排障的定位坐标、**选品研判与自迭代的业务背景**（实体和关系就是业务地图，归因沿关系走）。
> 所有环节说数据，必须用这里的名词，不许自己造词，主干链路顺序（见 ontology.png）。
> 本文只写正常业务视角；实验的内部设计（数据怎么造、陷阱怎么埋、画像数值）在 ontology_god.md，不给优化侧看。

## 1. 对象

### 热点单品 hero_item
| 字段 | 含义 |
|---|---|
| item_id | 当前就一个：google fitbit air |

### 配件簇 cluster（= SPU，选品和下发的对象）
选品卡评估的是它，下发给商家的也是它；商家基于它发出真实商品。

| 字段 | 含义 |
|---|---|
| cluster_id | 簇标识（唯一字符串） |
| price_range | 这个簇的典型价位带 |
| attrs | 这个簇的品在 材质/颜色/风格 等描述 |

簇实例不在本文维护，唯一出处：app/data/clusters.json。

### 站内销售趋势 on_site_sales（来源：我们自己平台）
粒度：群 × 簇 × 周 —— 自己平台，人群拆分拿得到。

| 字段 | 含义 |
|---|---|
| cluster_id | 哪个簇 |
| country | 哪个国家 |
| group_id | 哪个人群 |
| week | 哪周 |
| traffic | 流量 |
| orders | 订单 |

注意：真缺口的品类，站内没有供给、所以没订单，但用户搜索流量是存在的。

### 站外销售趋势 off_site_sales（来源：竞对平台 SHEIN / Temu 等）
粒度：簇 × 国家 × 周 —— 别人的平台拿不到人群拆分，粒度只能到国家。

| 字段 | 含义 |
|---|---|
| cluster_id | 哪个簇 |
| country | 哪个国家 |
| week | 哪周 |
| sales | 竞对销量 |
| price_band | 竞对售价带（给定价和补贴当参照） |

### 站外需求 off_site_demand（来源：YouTube / 对应国家本地论坛 / Google Trends）
粒度：簇 × 国家 × 周。采集路径和两份销售数据不同：拿着大单品去搜（"fitbit air 臂带"这类词），分析用户声音，再按簇关联回来。

| 字段 | 含义 |
|---|---|
| cluster_id | 哪个簇 |
| country | 哪个国家 |
| week | 哪周 |
| buzz | 社媒声量 |
| search_trend | 搜索趋势 |
| pain_posts | 痛点帖量 |

> 三个 [站内销售、站外销售、站外需求] 都是选品卡研判的直接输入。

### 选品卡 selection_card（对一个簇的综合评估）

| 字段 | 含义 |

| reason | 理由 |
| confidence | 信心 |

### 激励方案 incentive（跟着选品卡一起下发）
| 字段 | 含义 |
|---|---|
| card_id | 标识 |
| cluster_id | 激励哪个簇 |

### 消费者群 consumer_group

| 字段 | 含义 | 谁消费 |
|---|---|---|
| group_id | 群标识（唯一字符串） | — |
| country | 国家 | - |

## 2. 关系

### 主干链路（谁产生谁、谁流向谁）

```text
热点大单品 ──找出相关配件──▶ 配件商品簇
配件商品簇 ──数据统计──▶ 站内销售趋势 / 站外销售趋势
热点大单品 ──拿单品搜配件需求，按簇关联──▶ 站外需求
三份数据 ──研判哪个簇未来是新星──▶ 选品卡
选品卡 ──新星簇给多少价格激励──▶ 激励方案
选品卡 & 激励方案 ──打包成下发包──▶ 商家
商家 ──采纳后参考商品簇发布──▶ 新商品
消费者人群 ──购买──▶ 新商品
新商品 ──累计 7 日销量──▶ 破零率（目标）
```

### 业务影响关系（沿主干链路顺序，正常业务视角）

**热点大单品**：一切的起点。它卖火了，买它的人随之产生配件需求 —— 找什么配件、搜什么词，都围绕它展开。

**配件商品簇**：全链路的串联锚点。三份数据按簇统计、选品选的是簇、激励跟着簇、商家基于簇发品、破零算到簇发出的品上。平台每期从大类目池里圈选一批候选簇给选品研判，每期候选不同——像真实运营的每期候选池。

**三份数据**（都按簇统计，各照一个侧面）：

- **站内销售**：自己平台的现状 —— traffic 反映兴趣（搜了买不到，流量也在），orders 反映兴趣 × 供给（没供给就是 0 单）。自家地盘，能拆到人群（group_id）。
- **站外销售**：竞对平台已经承接掉的需求 —— 有销量说明需求真实、被验证过；price_band 是我们定价和补贴的参照。别人平台拆不到人群，按国家（country）看。
- **站外需求**：用户"想要"的需求信号 —— 围绕大单品，会搜、会聊、会吐槽，是能看到配件需求。也按国家看。
- 人群关联：群有 country —— 站内数据直接按群看，站外两份数据按国家采集、以国家和消费者群建立关联。

**选品卡**：读三份数据，研判哪个簇未来是新星。判据是三层对照：**站外需求涨 + 站外销售涨 + 站内有需求没供给 = 就是新星机会**。选错簇 → 商家发了也没人买 → 不破零。

**激励方案**：跟着选中的簇一起下发。lead 说给商家听（撑起他对这个品的预期），subsidy 补给消费者。给少了两头失效：商家不心动不发；消费者觉得贵不买。

**商家**：接到卡和激励，对着自己的生意算 —— 这个簇和我 top_categories 搭不搭（跨品类有能力边界：工厂只能做产线工艺相近的品，贸易商供应链要够得着，完全不沾边的不敢上）、信不信任平台建议（trust 低不接）、monthly_gmv 或 是不是工厂，撑不撑得起试新品。不发 = 这条下发直接计零 —— 破零率分母是下发数。

**新商品**：商家发出的真实 SKU。样子（attrs）和价格（price）商家自己定（参照簇的描述和价位带），平台只控 subsidy。实付价 = price − subsidy —— 是商家定价离谱还是补贴不够，得分清。

**消费者人群**：按自己的喜好和钱包投票 —— 不喜欢（taste vs attrs）不买；实付价超心理价位带不买（超多少才放弃，因群而异）；同类品会和竞对比价，明显贵了不买、明显便宜买的人更多。买 = 订单。

**破零率**：新品发布起 7 日销量累加 ≥ 5 单 = 破零（线定在 5：错推的品蹭不过去、擦线波动不左右结果；数值在 app/lib/consts.js），回填 sales_7d。分子是破零品数，分母是下发数 —— 以下发数作为分母，从而可以反映更多环节影响，选品/激励 -> 商家采纳 -> 消费者买单。

**环境规则**：每簇最多一个新品，不存在同簇分流；单个商家一轮最多接 2 个新品；问商家的顺序每轮不同，前面拒的包顺延给后面的商家。

## 3. 规则

1. **本体唯一出处**：本体和关系定义，约束基本业务规则。
2. **结构保持一致**：加本体/改字段 = 结构改动，链路各段都得跟着对一遍、一起修改。
3. **视角分离**：本文只写业务视角，可以喂给选品研判和自迭代当背景；实验内部设计一律写 ontology_god.md，不进优化循环。
